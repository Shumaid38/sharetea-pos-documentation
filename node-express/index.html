Sharetea Node.js + Express + PostgreSQL lab

Author: Humaid Syed

This read-only Express application connects to the existing Sharetea PostgreSQL database through pg. It renders the menu with EJS, filters by category using a parameterized query, and exposes live connection evidence at /api/health. It does not create tables, seed data, or change orders or inventory.

Run the application

Use Node.js 22 or newer. From the project root:

cd web-lab
npm ci
cp .env.example .env

Skip the copy step if .env is already configured. Edit .env locally with your database host, port, name, user, and password. Do not paste the password into source code or the terminal command line. src/config.js loads this file regardless of the working directory. Exported environment variables take precedence.

For the class AWS RDS database, obtain the public CA bundle from AWS:

mkdir -p .certs
curl --fail --silent --show-error \
  https://truststore.pki.rds.amazonaws.com/us-east-1/us-east-1-bundle.pem \
  -o .certs/rds-us-east-1.pem

Set DB_SSL=true and DB_SSL_CA to the absolute path of that file. Use the canonical RDS hostname supplied for the class database: the classroom DNS alias may not match the certificate. On macOS, dig +short <class-database-host> shows the canonical name. Verify the endpoint with your course information. Certificate verification remains enabled. For a local PostgreSQL instance without TLS, explicitly use DB_SSL=false.

npm run check:db
npm start

Open http://127.0.0.1:3000. The page shows the database name, server time, menu count, TLS status, and menu rows returned by PostgreSQL. Select a category and click Show menu. Stop with Ctrl+C; the server closes its connection pool. The server binds to this computer's loopback interface for the lab demo.

Evidence to show the TA

  1. Run npm run check:db, then npm start and open the menu page. Explain that Express handles the request, pg executes SQL, and EJS renders the result. Open http://127.0.0.1:3000/api/health to show a live query rather than a hardcoded connection message. A failed database query returns HTTP 503.

  2. From the repository root, run:

    git check-ignore -v web-lab/.env web-lab/node_modules/ web-lab/docs/ web-lab/.certs/
git ls-files web-lab/.env
git status --short --untracked-files=all web-lab

    The first command identifies the ignore rules. The second must print nothing: the credential file is not tracked. Show .env.example instead of .env. Commit the connection code, example configuration, package.json, and package-lock.json; ignore actual credentials, installed dependencies, local certificates, and generated documentation in this source repository.

  3. Open the publicly hosted documentation:

    • Node.js/Express API documentation
    • Java POS Javadoc

    Show the documented modules and Humaid Syed author tags. These are static GitHub Pages documents; the Express app and database credentials stay local. The TA still needs to observe your demonstration to give the checkoff.

Validation and documentation

npm test
npm run check:db
npm run docs

npm test uses test doubles and makes no database connections. It covers query parameter binding, HTML escaping, invalid input, database failures, configuration, and empty results. check:db is the separate live database verification.

JSDoc generates docs/index.html from the source comments and this guide. Published documentation is a snapshot: regenerate and copy docs/ into the documentation repository's node-express/ directory to update it. The JSDoc configuration omits source-file listings. Never copy .env, .certs, or database query results into the public documentation repository.

Files and behavior

File Purpose
src/config.js Load and validate environment variables and TLS options
src/db.js Create a bounded pool; query connection evidence, menu, and categories
src/app.js Express routes, input validation, rendering, and safe errors
src/server.js Listen locally and close connections on shutdown
src/check-db.js Run a real SQL query from the terminal
views/index.ejs Escape database text and render the menu
.env.example Share configuration names without credentials

The existing table must include menu_item(item_id, name, price, category, availability_status). No employee information or order history is exposed. Connections request PostgreSQL's read-only transaction default and use bounded connection and query timeouts. There is no authentication; keep the demo local.
